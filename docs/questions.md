## Business Logic Questions Log

### 1. How does the evaluation state machine work, including reminders and make-up evaluations?
- **Problem:** The prompt defines five states (Not Started, In Progress, Submitted, Returned for Revision, Archived) with a daily 9:00 AM digest, deadline feedback, and optional 5-business-day make-up windows — but does not specify who triggers each transition, how the make-up window is gated, or how the reminder digest is assembled.
- **My Understanding:** Evaluators drive forward-only progression up to Submitted, Reviewers hold the return/approve gates, and make-up is an Administrator-enabled flag evaluated against business days (not calendar days) after the cycle deadline.
- **Solution:** Transitions — `NOT_STARTED → IN_PROGRESS` (first save by the assigned Evaluator); `IN_PROGRESS → SUBMITTED` (Evaluator submit, validates required fields and threshold flags); `SUBMITTED → RETURNED_FOR_REVISION` (Reviewer with required reason) or `SUBMITTED → ARCHIVED` (Reviewer approve); `RETURNED_FOR_REVISION → IN_PROGRESS` (Evaluator resumes); `ARCHIVED` is terminal. Deadlines are stored on the `evaluation_cycle` row; the per-assignment effective deadline equals the cycle deadline unless a make-up extension is active. Make-up windows are enabled per-cycle by an Administrator and extend the submit-only grace period by up to 5 *business days* (Mon–Fri, excluding a configurable facility holiday list); submissions within this window are accepted but stamped `late=true` and surfaced in audit. The 9:00 AM local-time digest is a per-user server-computed view that lists all assignments whose effective deadline is within 48h, all `RETURNED_FOR_REVISION` items assigned to the user, and any overdue items still within the make-up window; it is delivered as an in-app banner (not email) and regenerated on first user session after 09:00 local time.

### 2. How is the scoring ledger computed, and how are missing values and outliers handled?
- **Problem:** The prompt requires deterministic scoring with a traceable ledger per submission, template-driven handling of missing values (default to zero *or* exclude from denominator), and outlier flagging at default z-score > 3.0 without silently altering values — but does not define the ledger schema, the selection rule between the two missing-value strategies, or how outlier bounds are parameterized.
- **My Understanding:** Each submission produces an immutable calculation trace capturing every input, rule, and derived subtotal; missing-value strategy is set per item on the template; outliers are flagged but never rewritten.
- **Solution:** Each `submission` row spawns one `calculation_trace` row referencing `template_version_id` and `rule_set_version_id` (both immutable snapshots at submit time) plus a JSONB `inputs` payload and a list of `trace_steps` — one per scored item — storing: raw value, effective value after missing-value handling, weight, subtotal contribution, and flags (`missing`, `outlier`, `threshold_exceeded`). Missing-value strategy is a per-item field on the template: `ZERO_FILL` (treat missing as 0, full denominator) or `EXCLUDE_FROM_DENOMINATOR` (skip the item and reduce the denominator proportionally); the chosen strategy is recorded on the step so reviewers can see which path applied. Outlier flagging runs against a per-item statistical bound — default z-score > 3.0 computed from the cycle's prior submissions, configurable per template item to an absolute range `[min, max]` or a different z threshold — and emits a flag without modifying the stored raw value. Recalculation is deterministic: replaying the same inputs against the same template and rule-set versions produces a byte-identical ledger (JSON canonicalized, float math replaced with `Decimal`).

### 3. How does build plan versioning, BOM diffing, and share link issuance work?
- **Problem:** Plan Owners can create, copy, and compare plan versions with per-change BOM diffs, generate offline export files, and issue time-limited share links that require a local login and role permission — but the prompt does not define immutability of versions, diff semantics for moved/renamed items, export format, or share-link token scope.
- **My Understanding:** Every plan version is immutable once saved, diffs are computed at the BOM-line level with a stable identity, and share links are authenticated bearer-grants scoped to a single plan version.
- **Solution:** `plan_versions` rows are immutable after save — edits produce a new version pointing back at `parent_version_id`. Each BOM line carries a `line_identity_key` (owner-chosen, stable across renames) so diffs classify changes as `ADDED`, `REMOVED`, `QUANTITY_CHANGED`, `PART_CHANGED`, or `NOTE_TAG_CHANGED`; moved lines keep the same identity and surface as a single change record. Compare endpoint returns a structured diff plus per-change notes and tags. Export is a signed `.zip` bundle containing `plan.json` (version metadata + full BOM), `diff.json` (vs parent), and a detached `signature` (HMAC over a manifest hash using the local KEK) for offline tamper detection. Share links issue a short bearer token scoped to `(plan_version_id, role, expires_at)` with max TTL 7 days; the token is still rejected unless the recipient has an active local login *and* the configured role permission (`build_plan:view_shared`). Revocation is immediate via `/plans/share-links/{id}:revoke`; all share events (issue, open, revoke) append to the audit log.

### 4. How do model registration, A/B traffic routing, and rollback interact with feature consistency?
- **Problem:** ML Engineers register models by version, route selected versions to low-latency inference (p95 ≤ 150 ms), and operate an A/B split (default 90/10) with one-click rollback if metrics degrade; the prompt also requires blocking promotion when training and inference feature definitions diverge — but does not specify how feature divergence is detected, what metric thresholds trigger rollback, or how routing is sticky.
- **My Understanding:** Feature definitions are captured as a signed schema alongside the model; routing is sticky per request-subject; rollback is a single atomic write that cuts the split.
- **Solution:** Each registered model stores a `feature_schema_hash` computed from the ordered list of feature names, dtypes, transformations, and source query hashes. Promotion to `APPROVED` (routable) is blocked unless the inference service's current feature schema hash matches the model's — divergence returns a 409 listing the differing features. Routing rules live in `inference_routing` as `(model_a_id, model_b_id, weight_a, weight_b)` with default `(90, 10)`. Request routing is sticky by `subject_key` (user id, session, or caller-provided idempotency key) via `hash(subject_key) mod 100` < `weight_a`, guaranteeing a subject sees the same arm across retries. Rollback is a single atomic update that sets `weight_a = 100, weight_b = 0` and captures the trigger (metric-based or manual) in `experiments.rollback_events`. Auto-rollback fires when any configured guardrail metric breaches its threshold over a rolling window (defaults: error rate > 2%, p95 latency > 150 ms, or feedback-derived disengagement rate exceeds baseline by > 30% over 15 minutes, all evaluated server-side). All routing changes append an audit row tagged `model_promotion` or `routing_change`.

### 5. How do end-user feedback events (Like, Not Interested, Block) flow into model behavior, and how are experiments gated?
- **Problem:** Embedded feedback controls drive near-real-time impact governed by experiment toggles and version rollback — but the prompt does not define the feedback event schema, how "near-real-time" impact is bounded, or how toggles prevent feedback from polluting a rolled-back arm.
- **My Understanding:** Feedback is a per-subject event stream that feeds a per-arm ranking signal; toggles both gate ingestion and gate consumption.
- **Solution:** Feedback events write to `feedback_events` with `subject_key`, `target_id` (item/content being rated), `event_type` (`LIKE` | `NOT_INTERESTED` | `BLOCK`), `model_version_id` (the arm that served the impression), `experiment_id`, and `created_at`. `BLOCK` is authoritative and persistent: the (subject, target) pair is suppressed from future ranking within that experiment regardless of toggle state. `LIKE` and `NOT_INTERESTED` feed a rolling per-arm signal with ≤60s propagation to the inference cache. Each `experiment` row carries two independent toggles: `ingest_enabled` (accepts new events into the arm's signal) and `apply_enabled` (allows the arm's signal to influence ranking). A rollback flips both to `false` on the losing arm and stops consumption; events continue to be *recorded* (for audit) but are not ingested into the signal store, so rolling back does not retroactively corrupt the restored arm. Rate-limit per subject: 60 feedback events/min (409 `rate_limited` beyond).

### 6. How do RBAC, sensitive-field masking, audit trails, and backup/restore interact?
- **Problem:** The prompt requires per-role gating across five roles, UI-default masking with database-level encryption at rest, append-only audit logs for five named actions (add/drop, rule changes, grade edits, plan rollbacks, model promotions), and a one-click restore restricted to Administrators — but does not specify how masking composes with audit payloads, what "add/drop" covers, or how restore interacts with encryption keys.
- **My Understanding:** Audit entries store identifiers and change shape (not raw sensitive values), masking is applied in the API layer on read, and restore requires re-binding the KEK before any encrypted column is readable.
- **Solution:** Roles carry resource-action permissions plus a `field_view_allowlist` that unlocks specific sensitive fields (e.g., evaluator notes, full grade values, subject identifiers); the API layer applies masking on response serialization so even cached replies respect the caller's allowlist. Sensitive columns are encrypted at rest using PostgreSQL's pgcrypto with a KEK loaded from an operator-mounted file at service start; the DB never holds the KEK. Audit actions covered: `PARTICIPANT_ADD_DROP` (assignment roster changes), `RULE_CHANGE` (template/rule-set version activations), `GRADE_EDIT` (any evaluation field change after initial save, with old/new values captured but encrypted at the column level — audit row stores only ids, actor, timestamp, and a content hash), `PLAN_ROLLBACK` (build-plan version activations that revert to a prior parent), and `MODEL_PROMOTION` (any routing_change or approved-version switch). The audit table has no UPDATE/DELETE endpoint and is index-organized by `(actor_user_id, created_at)` for fast queries. Backups are nightly `pg_dump` archives encrypted with the KEK, retained 30 days on a mounted local volume. Restore is a two-phase Administrator-only workflow: (1) select archive → service enters maintenance mode, rejects non-admin traffic, verifies the KEK decrypts the archive header, restores into a staging schema, (2) Administrator confirms → atomic swap to live schema; the entire sequence writes a `BACKUP_RESTORE` audit entry including archive id, KEK fingerprint, and Administrator id. Authentication baseline: local username + password ≥12 chars with salted hash, lockout after 5 failed attempts in 15 minutes, signed session tokens with 60-second anti-replay skew.
